## 一、定位（主人已定调，三方不得重议）

1. 本插件 = 把 CTX 里的 `op:search` 整条（含 query 聚合腿、url/page 腿、反爬五段）整体拆出后的独立产品；主人定性「现在的 SEARCH() 跟 PAGE() 基本就是一个 FP 雏形」。
2. 与 §14.3 的关系：主人当晚「FETCH 超出插件范围」的判决，经 16.1-1 重归类后覆盖 page() 整条——拆 FP 是该判决的执行到位，不是新决策。
3. **入库接口（FP 正文 → CTX 库）先不做**（16.1-2 括注）。现阶段"网页要入库"= 模型拿 FP 文本 → `ctx op:index {content}` 两步中转。
4. **【v2.1 主人裁决 13:1x，逐字】**：「现有 OP SEARCH 全部搬出去，不是让你们做筛检选择，是把三方讨论结果-三堆分类-20261108 中已有的功能都带出去」＋「**只有 OP SEARCH 的内容带出去，不是整个 CTX 的功能**」。⇒ 边界双向钉死：**FP = `op:search` 这一条能力的全部承载**（query 腿 + page/url 腿 + 反爬五段 `fp/`+`deps/pylibs` + 17 卡 + offline 卡 + 底座五件 + url-guard 及其依赖），一件不裁；**CTX = 其余全部功能原地不动**（记忆库/run/recall/index{path,content,dir}/压缩/门与自测）。"简单版"= 不加 fetch/下载/入库这些**新**东西，**不是**裁既有能力。
5. ⇒ **原 §四-3「第一刀切不切」的问题随裁决消失**：`fp/` + `deps/pylibs`（6.65 MB = 预放 98%）**必带**。"page 裸抓腿不依赖 fp、裁腿省体积"的技术账只对"要不要裁"成立——主人已答不裁，该账降级为备查。
6. **【事实补注〔M10〕】** `page()` 在 CTX 工具面 0 调用的成因 = 宿主 schema 从来没有 url 入口（1299/1299 header 无 url 键；唯一带 url 的 `web_fetch` 10-26 起消失）——不是不爱用。**这不构成裁 page 腿的理由**（裁决第 4 句），只构成"FP 上线第一天 A-10 参数宽容必修"的理由。
7. **【v2.1 主人追加定性 13:2x，逐字】**「相当于把"三方讨论结果-三堆分类-20261108"都实现以后，拆封成CTX跟FP两个插件，功能跟"三方讨论结果-三堆分类-20261108"后是一样的，FP就是搬出去的OP SEARCH」。⇒ 三点直接含义：① **《三堆分类》文件的全部既定项 = 实现基准**（§九 七决议、A 堆各件、N12 全套、G-probe、B 堆各已决项、C 堆探针），拆封时**一条不许丢**；② **拆封只改落点、不改功能总量**——同一套既定功能分装进两个插件（§16.3「只改落点，不推翻任何已签结论」的同一条话）；③ **FP 的交付物 = `op:search` 那条能力在三堆文件里的全部既定项**（§16.3 已点名落 FP 的：A-1/A-3/A-5/A-7a/A-8(重算基准)/A-9、N12 全套+G-probe、B-3/B-13/B-5/B-11/B-10、B-6 的 media 接线、§12.9-3 contentType、§13.3 前置①／§14.6／§十五 B-12 的 302）；A-10 两边各留一份（§16.3"拆插件治不了它"）。
